# PROMPT — Diagnosticar, corrigir e testar a API do Finance Micro SaaS

## 1. Objetivo principal

Quero que você assuma a responsabilidade de diagnosticar, corrigir e validar o problema de comunicação entre a API do meu projeto Finance Micro SaaS, hospedado na Vercel, e o Google Apps Script, que utiliza uma planilha do Google Sheets como banco de dados.

**O objetivo é entregar o aplicativo funcionando corretamente, com a API conseguindo consultar e retornar os dados reais da planilha.**

Não quero apenas uma análise, sugestões ou um relatório de possíveis causas. Quero que você investigue o problema, implemente as correções necessárias, execute os testes e entregue a solução validada.

## 2. Contexto importante

O código do aplicativo frontend funciona perfeitamente. Não quero que você refaça o aplicativo nem altere funcionalidades que já estão funcionando.

O problema atual está na API e na conexão entre os serviços.

O projeto utiliza a seguinte arquitetura:

- **Frontend:** interface do Finance Micro SaaS.
- **API:** endpoint serverless hospedado na Vercel, no arquivo `api/finance.js`.
- **Backend de dados:** Google Apps Script.
- **Banco de dados:** Google Sheets.

A comunicação deve seguir o fluxo:

Frontend → API da Vercel → Google Apps Script → Google Sheets → Google Apps Script → API da Vercel → Frontend.

O aplicativo precisa conseguir consultar os dados da planilha e apresentar as informações corretamente na interface.

## 3. Alterações e configurações já realizadas na Vercel

Já configurei o projeto na Vercel e realizei alterações relacionadas à conexão da API.

Considere as seguintes informações:

1. O projeto está hospedado na Vercel.
2. O arquivo responsável pela API é `api/finance.js`.
3. Foram configuradas as variáveis de ambiente:
   - `APPS_SCRIPT_URL`: URL completa do deployment do Google Apps Script, terminada em `/exec`.
   - `APPS_SCRIPT_SHARED_SECRET`: segredo compartilhado utilizado para autenticar a comunicação entre a API e o Apps Script.
4. A proteção de acesso da Vercel está habilitada para todos os deployments. Essa proteção deve ser preservada, pois o aplicativo é de uso pessoal.
5. Já realizei testes no endpoint da API da Vercel pelo navegador e pelo DevTools.

Um dos testes apresentou a seguinte requisição:

`GET /api/finance?acao=dashboard&t=1793310456424`

O resultado foi `200 OK`, mas isso, isoladamente, não comprova que os dados da planilha estão sendo consultados e retornados corretamente.

**Não presuma que a conexão está funcionando só porque a API responde com HTTP 200.** Verifique também o corpo da resposta, o conteúdo retornado pelo Apps Script e os dados efetivamente recebidos pelo frontend.

Não exponha o segredo compartilhado no frontend, em logs públicos, em respostas de erro ou no código-fonte público.

Se precisar alterar variáveis de ambiente, preserve os valores válidos existentes sempre que possível. Não invente novos segredos nem substitua configurações sem necessidade.

## 4. Código do Google Apps Script

O código atual do Google Apps Script estará disponível no arquivo:

**`apps script.txt`**

Leia esse arquivo integralmente antes de realizar alterações.

Analise o funcionamento do `doPost`, do `doGet`, das funções de consulta à planilha, da autenticação por segredo compartilhado e da serialização das respostas JSON.

Verifique especialmente se as funções de consulta estão retornando objetos JavaScript comuns ou objetos `ContentService.TextOutput`, e se existe alguma serialização duplicada capaz de produzir respostas vazias, como `{}`.

Essa é uma hipótese que precisa ser investigada, não uma conclusão que deve ser aceita sem testes.

Não presuma que o problema está exclusivamente no Apps Script ou exclusivamente na Vercel. Investigue toda a cadeia de comunicação e identifique a causa real.

## 5. Diagnóstico obrigatório

Inspecione o projeto e identifique a causa raiz do problema.

Verifique, no mínimo:

- Se `api/finance.js` está recebendo e interpretando corretamente os parâmetros das requisições.
- Se as ações suportadas pelo endpoint correspondem às ações esperadas pelo Apps Script.
- Se a variável `APPS_SCRIPT_URL` contém a URL correta e aponta para o deployment adequado.
- Se o deployment do Apps Script está atualizado e acessível para as requisições autenticadas.
- Se o método HTTP, o corpo da requisição e o formato dos parâmetros estão corretos.
- Se o segredo compartilhado está sendo enviado e validado corretamente.
- Se as permissões de execução do Apps Script permitem o acesso necessário à planilha.
- Se o Apps Script está lendo a planilha correta e encontrando os dados esperados.
- Se as respostas do Apps Script são serializadas corretamente em JSON.
- Se a API da Vercel está interpretando e encaminhando essas respostas sem perder informações.
- Se a proteção da Vercel, redirecionamentos, erros de autenticação, cache ou configurações de deployment estão interferindo nas requisições.
- Se existem erros silenciosos, tratamento inadequado de exceções ou respostas de sucesso emitidas mesmo quando a consulta falha.

Utilize os logs disponíveis, o código existente e testes controlados para distinguir claramente cada etapa.

## 6. Corrija o problema de forma definitiva

Após identificar a causa raiz:

1. Implemente as correções necessárias na API.
2. Corrija o Google Apps Script, caso seja necessário.
3. Preserve o funcionamento do frontend.
4. Preserve a autenticação e a proteção de acesso existentes.
5. Evite alterações desnecessárias na arquitetura.
6. Não remova validações de segurança apenas para fazer os testes passarem.
7. Não substitua a integração real por dados fictícios, mocks ou respostas estáticas.
8. Não considere uma requisição bem-sucedida se a API estiver retornando dados vazios indevidamente.
9. Garanta que erros sejam tratados e reportados de maneira útil, sem expor segredos.

Se houver necessidade de publicar uma nova versão do Apps Script, explique essa necessidade, realize a atualização se tiver acesso autorizado e confirme qual deployment deve ser utilizado.

Se alguma configuração precisar ser atualizada manualmente por mim na Vercel, informe exatamente o que deve ser alterado, onde e por quê. Não presuma que uma alteração no código atualiza automaticamente as variáveis de ambiente ou o deployment publicado.

## 7. Testes obrigatórios antes da entrega

**Não entregue o trabalho apenas porque o código compila ou porque a API retorna HTTP 200.**

Execute os testes reais possíveis e valide o caminho completo entre a API e a planilha.

### Teste 1 — Conectividade

- Confirmar que a API da Vercel consegue chamar o Google Apps Script.
- Confirmar que o Apps Script recebe e valida a autenticação.
- Confirmar que a consulta à planilha é executada.

### Teste 2 — Dashboard

- Consultar a ação `dashboard`.
- Verificar se a API retorna um JSON válido.
- Conferir se os dados retornados correspondem aos valores reais da planilha.
- Confirmar que o frontend consegue utilizar esses dados.

### Teste 3 — Histórico

- Consultar a ação `historico`.
- Confirmar que os registros reais da planilha são retornados no formato esperado.
- Verificar se a resposta não está sendo transformada indevidamente em `{}` ou em uma lista vazia.

### Teste 4 — Demais consultas

Testar as demais ações de leitura implementadas pelo projeto, incluindo, quando existentes:

- `subcategorias`;
- `configuracoes`;
- `metas`.

Validar os formatos das respostas e a compatibilidade com o frontend.

### Teste 5 — Segurança e erros

- Confirmar que a API continua protegida.
- Verificar o comportamento diante de autenticação inválida, parâmetros inválidos e falhas de comunicação.
- Garantir que os erros não revelem o segredo compartilhado.
- Confirmar que as falhas não sejam apresentadas como consultas bem-sucedidas.

### Teste 6 — Regressão

- Verificar se as correções não quebraram as funcionalidades já existentes.
- Confirmar que o frontend continua funcionando.
- Validar as principais telas e operações relacionadas aos dados financeiros.

## 8. Critérios objetivos de aprovação

O trabalho só poderá ser considerado concluído quando:

- A API da Vercel conseguir consultar o Apps Script.
- O Apps Script conseguir acessar a planilha correta.
- A ação `dashboard` retornar os dados reais esperados.
- A ação `historico` retornar os registros reais esperados.
- As demais consultas implementadas funcionarem corretamente.
- As respostas forem JSON válidos e compatíveis com o frontend.
- O aplicativo apresentar os dados corretamente na interface.
- Não houver erros conhecidos de conexão, serialização ou autenticação.
- A proteção de acesso continuar funcionando.
- Os testes realizados estiverem documentados, com resultados verificáveis.

Se não houver dados cadastrados na planilha, diferencie explicitamente uma planilha legitimamente vazia de uma falha de consulta. Não invente registros para fazer o teste passar.

5. **Evidências:** apresente exemplos das respostas reais da API, omitindo segredos e informações sensíveis.
6. **Estado final:** informe se o aplicativo foi efetivamente validado com dados reais da planilha.
7. **Pendências:** caso algo dependa de uma ação minha ou não tenha podido ser testado, explique com clareza.

Se você tiver acesso ao repositório, aos arquivos, à Vercel e ao Apps Script, faça as alterações e publique as versões necessárias dentro das permissões disponíveis.

Se não tiver acesso a algum serviço, não afirme que realizou uma publicação ou um teste que não conseguiu executar. Prepare a correção, explique a limitação e me dê instruções exatas para concluir a etapa necessária.
